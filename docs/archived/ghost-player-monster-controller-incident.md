# 幽灵玩家导致怪物控制停滞：事故报告与新架构设计约束

> 事故日期：2026-08-08  
> 报告日期：2026-08-09  
> 状态：原因链已基本确认；触发端的具体操作无法由现有日志唯一还原；**阶段 B（Twinkle 稳定层补强）已于 2026-08-09 实施完成**，后续线上沟通暴露的“前台正常、怪物控制子系统单独失活”盲区已纳入阶段 C 设计（见 §3.5、§5.5—§5.7、§六）
> 影响范围：旧服 `datas-server` 的怪物控制权；Twinkle 的连接存活、会话归属与热重载边界  
> 参考说明：事故取证与旧服行为理解参考 `datas-server`（GPL）。本文只记录事实与设计思路，不复制其代码；Twinkle 的 MIT 实现必须自研。

---

## 一、结论

1. **没有足够证据认定玩家“江枫渔火”开挂。** 事故时段未命中客户端完整性、攻击速度等外挂检测；包速告警均未达到确认阈值。
2. **第三次“幽灵玩家 V2”修复已经部署，但校验维度不足。** 它检查的是 Netty Channel 是否仍为 `active`、Client 与 Character 是否互相引用、角色是否仍在地图；本次残留连接恰好仍能通过这些检查，却已经不能正常承担怪物控制。
3. **地图卡怪的直接原因是怪物控制权长期绑定在失效 Client 上。** 该 Client 不再提供有效 `MOVE_LIFE`，但服务端仍把它当作可用控制者；其他玩家进图后拿不到控制权，于是看到整张图怪物静止。怪物被攻击时会因攻击/受击链路产生动作，死亡后也能刷新，因此并非地图 tick 或怪物对象整体停止。
4. **旧服最小修复可以只做 Client 级怪物移动租约。** 它足以解决“一个幽灵 Client 拖死整张图”，不需要本次同时重写登录、断线、换频道与 Character 生命周期。
5. **必须把“不控制任何活怪”定义为无检测状态。** 怪物被别人击杀、自然消失、换图清除，导致该 Client 控制的活怪数归零时，立即停止计时并清空本轮状态；不得踢人、降权、记异常或影响后续游戏。
6. **Twinkle 不应沿用旧服的单一 Idle 判断。** 传输存活、游戏行为活跃、怪物控制能力是三个不同信号；同时，所有在线表、断链清理和怪物控制绑定都必须带会话代际，防止旧连接迟到关闭时误删新连接。
7. **玩家能移动、攻击，不代表怪物控制能力正常。** 后续沟通确认客户端可能只丢失怪物控制循环，人物前台与网络收发仍工作；因此人物移动、攻击、`PONG` 都不能直接恢复怪物控制资格。
8. **阶段 B 的 Client 级聚合租约能止住“全无 `MOVE_LIFE`”，但还不是终局。** 当前任一受控怪的合法 `MOVE_LIFE` 会替同一 owner 的全部怪续租，单只失活可被其他怪掩盖；冷却结束后，同一坏客户端也可能重新拿回控制权。
9. **正确性不得依赖客户端主动断开。** 客户端退出前另建连接上报，可以作为加速清理的可选信号，但覆盖不了进程被直接杀死、断网和“仅怪物子系统失活”；服务端仍必须自行检测、回收和降级。

建议决策：

- **旧服**：仅实施 Client 级 `MOVE_LIFE` 租约与控制权释放，先止住卡图；不在同一补丁中重写完整会话生命周期。
- **Twinkle**：保留已完成的会话代际、分阶段心跳和稳定层租约；阶段 C 把怪物级首次响应、控制者能力隔离和服务端权威兜底纳入设计。热重载逻辑只能操作稳定层状态，不能自己持有计时与归属。

## 三、原因分析

### 3.1 已确认的失效链

```text
客户端停止正常游戏循环或连接进入半失效状态
  → 服务端 TCP Channel 仍显示 active
  → Client / Character / Map 引用关系仍完整
  → V2 校验继续认定该角色可用
  → 怪物控制权仍归该 Client
  → 不再收到有效 MOVE_LIFE
  → 后进入地图的正常玩家拿不到控制权
  → 全图怪物静止
  → 旧角色被清走或新登录触发归属变化后，控制权重分配，地图恢复
```

### 3.2 为什么第三次修复没有抓到

“幽灵玩家 V2”已经检查：

- 角色不是隐藏状态、仍为世界登录状态、未处于换图；
- 角色与怪物在同一地图；
- `client.getPlayer()` 仍指向该角色；
- Netty Channel 仍为 `active`；
- 地图容器内仍是同一个 Character 引用。

这些条件能抓“引用断裂”或“Channel 已关闭”的幽灵，但抓不到**连接对象仍活、游戏循环已经失效**的情况。`isActive()` 只说明本地 Channel 尚未关闭，不等于客户端仍在读包、回包，更不等于它还能控制怪物。

### 3.3 旧服 Idle 为何没有兜底

旧服使用的 `IdleStateHandler(0, 0, 120)` 是 `allIdle`：只有连接同时没有读、没有写才触发。服务端持续向幽灵连接发送地图/广播数据时，写活动会不断重置 `allIdle`，因此连接可能永远不进入空闲检测。

即便修正为读空闲，也不能把“多久没读到任意包”直接等同于“玩家应被踢下线”：

- 登录服允许玩家停在选角或创建角色界面；
- `PONG`、完整性包或后台包能证明传输层仍有响应，却不能证明怪物控制循环正常；
- 热重载或受控暂停可能短暂阻塞游戏逻辑，但不代表客户端失联。

### 3.4 触发操作能否确定

不能。现有日志只能确认旧会话在频道 2 留下残影，随后同一角色在频道 7 重新登录；无法唯一判断此前是正常下线失败、网络单向中断、客户端崩溃、强制关闭、切换过程异常，还是其他连接边界条件。

应修复的是服务端不变量：**不论客户端以哪种方式消失或重连，失效会话都不能无限持有怪物控制权，也不能清理新一代会话。**

### 3.5 后续沟通确认：这是子系统级失活，不一定是客户端整体挂死

新增现象是：玩家人物仍可能移动、攻击和收发普通游戏包，但怪物不管是否被攻击、是否死亡重生，都长期站着不动。它补充了原事故链：

```text
人物前台/网络循环仍工作
  → 服务端持续收到人物行为，TCP 也保持 active
  → 客户端怪物控制循环没有处理控制包，或不再发送 MOVE_LIFE
  → 服务端把普通活跃误当成控制能力正常（若用普通行为解除冷却）
  → 新刷出的怪继续分给同一失效控制者
  → 怪物死亡和重生只能更换怪物对象，不能修复控制者能力
```

怪物站着不动的根本原因不是“怪死没死”，而是当前协议把怪物移动结果交给唯一控制客户端产生，其他客户端只接收服务端转发。攻击、扣血、死亡和重生属于另一条链路；只要新怪仍分给同一个失效控制者，就会继续静止。

因此，传输心跳只能回答“连接能否通信”，人物行为只能回答“人物主循环是否活跃”，两者都不能证明怪物控制子系统可用。新建连接发送“旧会话已退出”也只能覆盖完整退出，不能覆盖本次这种局部失活。

## 四、旧服最小修复：Client 级怪物移动租约

### 4.1 修复范围

本补丁只负责：

- 识别“仍持有活怪控制权，但长期没有任何有效 `MOVE_LIFE`”的 Client；
- 释放该 Client 当前持有的全部怪物控制权；
- 在短暂冷却期内跳过该 Client，让地图内其他正常 Client 接管。

本补丁明确不负责：

- 立即移除幽灵角色贴图；
- 推断玩家是否开挂；
- 强制踢下线；
- 一次性重写断线、换频道、重复登录和 Character 对象生命周期。

这是有意的范围切分：先以小改动消除整图卡怪，再由新架构彻底处理会话归属。

### 4.2 状态机

状态放在运行期 `Client`，不得持久化进角色数据：

| 状态 | 条件 | 行为 |
|---|---|---|
| `IDLE` | 当前控制的活怪数为 0 | 不启动 `MOVE_LIFE` 计时，不影响玩家。 |
| `GRACE` | 从 0 只切到至少 1 只活怪 | 开始一轮新宽限期，旧时间戳不得沿用。 |
| `HEALTHY` | 收到并通过归属校验的 `MOVE_LIFE` | 更新该 Client 的最后有效怪物移动时间。任一受控活怪的有效包即可续租。 |
| `STALE` | 仍控制至少 1 只活怪，且超过租约仍无有效 `MOVE_LIFE` | 仅释放怪物控制权，进入短冷却；不踢玩家、不删角色。 |

只允许在 `MoveLifeHandler` 完成以下校验后续租：

1. 包内怪物仍存活且仍在当前地图；
2. 当前 Client 确实是该怪物的控制者；
3. 移动包通过既有序号/位置等合法性校验。

不能在解包前或仅凭 opcode 到达就续租，否则伪造、迟到或越权的 `MOVE_LIFE` 也会让坏控制者一直存活。

### 4.3 “怪物消失或被别人杀死”必须遵守的规则

这是本方案的硬验收条件：

- 怪物死亡、被其他玩家击杀、自然消失、地图卸载或控制权主动转移时，都要从原 Client 的“受控活怪集合/计数”中移除。
- 计数从 1 变为 0 时立即进入 `IDLE`，清空本轮 `leaseStartedAt` 与 `lastValidMoveLifeAt`。
- **自然归零不得进入冷却，不得累计异常次数，不得发警告，不得断线。**
- 以后再次分到第一只怪时，从新的 `GRACE` 开始，不能因旧时间戳立即被判过期。
- 只有“租约超时导致的主动释放”才进入短冷却，防止巡检下一轮立刻把怪物又分回同一个坏 Client。

因此，“地图暂时没有怪”“怪被别人杀光”不会影响玩家；检测只在“这个 Client 当前确实占着至少一只活怪的控制权”时生效。

### 4.4 巡检与阈值

- 复用现有地图巡检/控制者自愈任务，不新增高频线程。
- 租约按 Client 计算，而不是每只怪各算一个超时，避免对象和定时器膨胀。
- 初始阈值建议做成配置，先采用保守值（例如 45—60 秒），巡检周期沿用现有约 10 秒；最坏恢复时间约为“租约 + 一个巡检周期”。
- 现有包速统计排除了 `MOVE_LIFE`，最终阈值没有生产分布可依赖。上线前应先以观察模式记录：受控活怪数、最后有效 `MOVE_LIFE` 间隔、释放原因；确认没有静止怪的超长合法间隔后再开启强制释放。
- 误判的后果也应限制为“释放控制权”，绝不能升级为封号或踢线。

### 4.5 重新成为控制者

超时 Client 不是永久拉黑：

- 冷却到期后可以重新参与分配，并重新进入 `GRACE`；或
- 收到明确的前台游戏行为（玩家移动、攻击、完成换图）后提前解除冷却。

`PONG`、完整性包和自定义后台包不能单独解除怪物控制冷却，因为它们只能证明网络/辅助线程还在响应，不能证明游戏控制循环已经恢复。

### 4.6 最小验收用例

1. 正常 Client 控制多只怪，任一受控怪持续产生合法 `MOVE_LIFE`，不得释放。
2. Client 仍显示连接 active，但停止所有 `MOVE_LIFE`；超时后只释放它的控制权，其他玩家接管，地图恢复。
3. Client 控制的最后一只怪被别人击杀；立即进入 `IDLE`，经过任意时长都不得影响该 Client。
4. 地图清怪/卸载使控制数归零；不得进入冷却。
5. `IDLE` 很久后重新分到怪；必须获得完整新宽限期。
6. 伪造其他玩家控制怪物的 `MOVE_LIFE`；不得续租。
7. 地图只有失效 Client 时，释放后允许暂时无人控制；正常玩家后来进图后必须能接管。

## 五、Twinkle 的 Idle 与会话归属设计

### 5.1 当前实现存在的直接风险

截至本报告，Twinkle 当前代码有以下缺口：

1. `V83ServerInitializer` 配置了 `IdleStateHandler(0, 0, 30)`，仍然是 `allIdle`；`NetworkSession` 没有处理 `IdleStateEvent`。因此源码注释中的“心跳超时 30s 断链”目前并未真正实现。
2. 登录服和频道服复用同一个 Idle 配置，没有按 `SessionStage` 区分登录界面、选角/创建角色等待与游戏内连接。
3. `PlayerSessionRegistry.register(characterId, session)` 直接覆盖，`unregister(characterId)` 直接按角色 ID 删除。
4. 断链回调同样按角色 ID 删除在线表。如果旧连接被新连接替代后才迟到触发 `channelInactive`，旧回调可能把新连接的会话登记与新角色对象一起删除。

以上是对当前实现的代码核查结果，不代表本次已修改。

### 5.2 三类存活信号必须分开

| 信号 | 回答的问题 | 允许触发的动作 |
|---|---|---|
| 传输心跳 | 对端是否仍能读写协议包？ | 探测、确认失联后关闭连接。 |
| 前台游戏活动 | 玩家游戏主循环是否仍有正常行为？ | 作为控制者候选恢复、风控辅助；不能单独判定断线。 |
| 怪物控制租约 | 该会话是否仍能承担怪物控制？ | 只分配/释放怪物控制权。 |

不得用任意一个信号代替另外两个：收到 `PONG` 不等于会控制怪物；没有玩家移动不等于断线；没有受控怪时没有 `MOVE_LIFE` 更不等于异常。

### 5.3 分阶段心跳，而不是一个全局 Idle

建议由不可热重载的 Netty/会话稳定层负责心跳：

1. 使用 `readerIdle` 作为“发起探测”的触发器，不因读空闲直接踢线。
2. 发送带序号/期限的 `PING`，在规定期限内收到匹配 `PONG` 即恢复；超期才关闭。
3. `PONG` 处理作为所有合法会话阶段共享的稳定贡献点，登录、选角、创建角色、游戏内都能响应。
4. `SessionStage` 的业务停留时限与传输心跳分开配置：玩家可以长时间停在角色选择/创建界面，只要仍能正确回心跳就不应被误伤。
5. 热重载、DRAINING 或受控 tick 暂停时，心跳层保持运行；怪物控制租约应暂停计时或在恢复后统一增加宽限，避免批量误释放。
6. 所有期限使用单调时钟，避免系统时间校正造成误判。

### 5.4 会话代际是热重载与重连的共同边界

每条 TCP 连接创建不可变 `sessionId`；角色被某连接认领时再生成单调递增的 `sessionGeneration`。所有运行时归属都绑定：

```text
(characterId, sessionId, sessionGeneration)
```

至少包括：

- 在线会话注册；
- Character 运行时归属；
- 地图玩家索引；
- 怪物控制租约；
- 断链、换频道与超时清理命令。

关键规则：

- 新连接认领同一角色时生成新代际；旧代际的怪物租约立即失效。
- 断链清理使用 compare-and-remove，只能删除“仍由本 sessionId/generation 持有”的登记。
- 旧连接迟到关闭、旧逻辑迟到写入、旧定时任务迟到执行时，因代际不匹配只能成为空操作，不能清理新会话。
- 玩家持久化数据与 Character 纯数据中不保存 TCP Channel、计时器或控制租约；这些均属于稳定运行时状态。
- 热重载替换的是逻辑实现，不替换连接身份和代际状态。可替换逻辑只能经稳定接口申请、续租或释放控制权。

这比“新 Client 是否复活旧 Character 对象”更根本：对象可以重建，也可以在安全点复用，但**归属必须由代际证明，不能由对象引用相等或角色 ID 唯一性猜测。**

### 5.5 Twinkle 当前实现的覆盖范围与剩余盲区

阶段 B 当前实现采用 owner 级聚合租约，默认 TTL 50 秒、巡检 10 秒、超时冷却 15 秒、无主怪重分配 10 秒：

- 若某控制者完全停止发送所有合法 `MOVE_LIFE`，控制权会在约 50—60 秒内释放；地图内已有其他健康玩家时，可在同轮或下一轮重分配。
- 若地图里只有原控制者，冷却结束后仍可能在约 65—80 秒时重新分给它；如果其怪物控制子系统没有恢复，故障会循环出现。
- 任一受控怪的合法 `MOVE_LIFE` 会续租整个 owner。一个仍会回包的怪可以掩盖同 owner 下其他长期无响应的怪。
- `SPAWN_MONSTER_CONTROL` 发出后没有独立的首次响应确认；发送失败、客户端未处理控制包和客户端局部失活，只能等聚合 TTL 兜底。
- 当前人物移动或攻击不会直接续怪物租约，这是正确的；阶段 C 也不得把它们作为恢复完整控制资格的依据。

所以阶段 B 已完成的是**全失活止血与会话安全地基**，不是“每只怪都保证有响应”的终局。

### 5.6 阶段 C：分层控制租约（兼容现有客户端的主方案）

租约改成两层，且不为每只怪创建独立线程或定时器，仍由地图 tick 批量扫描：

| 层级 | 身份与状态 | 职责 |
|---|---|---|
| 怪物分配层（权威） | `(mapInstanceId, monsterOid, assignmentGeneration, ownerSessionId, ownerGeneration)` | 记录控制包发出时间、首次有效响应、该怪最后有效响应、重试次数和释放原因；一只怪的响应不能替其他怪续租。 |
| owner 能力层（熔断器） | `(characterId, sessionId, sessionGeneration)` | 聚合连续分配失败率；多只怪首次响应失败时快速隔离该 owner，避免继续把整图怪物分给它。 |

建议状态机：

```text
UNOWNED
  → ASSIGNED_WAIT_FIRST_RESPONSE（发控制包，启动首次响应期限）
  → ACTIVE（收到该怪、该 owner、当前分配代际的合法 MOVE_LIFE）
  → SUSPECT（首次响应或活动期限到期，限次重发控制包）
  → UNOWNED（仍无响应，释放并优先改派其他 owner）
```

硬规则：

1. 只有通过怪物存活、地图实例、owner 会话代际、当前分配关系及移动合法性校验的 `MOVE_LIFE`，才能确认或续该只怪的租约。
2. 分配后必须有独立“首次响应期限”；限次重发后仍无响应，释放该怪并将该 owner 的怪物控制能力置为隔离/观察态。
3. 恢复资格必须通过小规模控制探针：先只分一只明确需要客户端控制且会产生移动响应的怪，成功后再逐步放量；人物移动、攻击、心跳只能允许进入观察态，不能直接恢复全部资格。
4. 静态、脚本冻结或设计上无需移动响应的怪必须显式标记为 `responseRequired=false`，不参与无响应判定，避免合法静止被误杀。
5. 优先改派未失败的其他 owner；没有其他候选时，可以限次向原 owner 重发/探测，但不得无限重复分配并把地图永久判为正常。
6. 旧分配代际的异步回调不得修改新分配。现有 v83 包不携带分配代际，因此同一会话刚失败后不应立即拿回同一怪；若将来扩展客户端协议，才可把 `assignmentGeneration` 作为显式回包令牌。
7. 怪物死亡、消失、地图实例卸载、玩家离图、会话替换时，由稳定状态层幂等释放；热重载或 tick 受控暂停时统一冻结/补偿期限，所有时间使用单调时钟。

这套方案保证：**只要地图内至少存在一个怪物控制子系统正常的客户端，静止怪能在配置上限内自动改派恢复。**

### 5.7 真正终局：服务端权威怪物移动

只要服务端仍把怪物 AI/移动结果完全委托给客户端，就无法在“所有候选客户端的怪物控制子系统都失效”或“地图只有一个坏候选”时保证怪物一定会动。租约只能检测与换人，不能凭空产生移动。

要从架构上彻底消除这类故障，最终应把客户端从“控制权拥有者”降为“移动提议者/兼容加速器”：

- 服务端拥有怪物位置、AI 状态、目标、技能和移动序号的权威状态；客户端 `MOVE_LIFE` 只作为经过校验的移动提议。
- 正常情况下可继续采用客户端控制以保持 v83 行为与性能；租约失败且无健康候选时，切换到服务端最小 AI 兜底并广播移动。
- 完成地图物理、寻路和技能 parity 后，再决定是否把服务端兜底提升为默认权威模拟。

这是工作量较大的长期路线，但它是“无健康客户端时也保证怪物不冻结”的唯一完整保证。阶段 C 的分层租约是兼容性强、风险低的前置措施，两者不冲突。

## 七、可观测性与完成标准

建议新增结构化字段/指标：

- `characterId`（日志中按现有脱敏规范处理）、`sessionId`、`sessionGeneration`；
- 当前受控活怪数、最后有效 `MOVE_LIFE` 距今时间；
- 每怪 `mapInstanceId/monsterOid/assignmentGeneration`、控制包发出时间、首次响应延迟、最后有效响应、重试次数；
- owner 控制能力状态、探针成功/失败、隔离次数，以及“人物仍活跃但怪物控制无响应”的计数；
- 控制权释放原因：`LEASE_EXPIRED`、`MONSTER_DIED`、`DESPAWNED`、`MAP_LEFT`、`SESSION_REPLACED`；
- 旧代际清理被拒次数；
- 地图无可用控制者时长、控制权重分配耗时；
- 心跳探测次数、PONG 超时次数，按 `SessionStage` 分组。

完成标准：

1. 构造“Channel 仍 active、但不再发 `MOVE_LIFE`”的客户端，地图能在配置上限内恢复。
2. 目标 Client 不控制活怪时，无论停留多久都不因怪物租约受到任何影响。
3. 旧连接在新连接登录后迟到关闭，不能移除新会话、新 Character 或其地图登记。
4. 登录/选角/创建角色界面长时间停留，只要心跳正常就保持连接。
5. L3 热重载前后 sessionId/generation 不变，怪物租约不因逻辑对象替换而误过期。
6. 玩家持续发送人物移动/攻击，但不发送任何 `MOVE_LIFE`；怪物仍须在配置上限内改派，人物行为不得替怪物续租或直接解除隔离。
7. 同一 owner 控制多只怪，仅其中一只持续回包；其他需要响应的怪必须分别超时并改派，不能被聚合续租掩盖。
8. 控制包发送后始终没有首次响应；限次重发后必须释放，且后续只允许该 owner 通过单怪探针恢复。
9. 旧会话、旧地图实例或旧分配代际的迟到移动/回调不能续新租约。
10. 地图只有一个失效候选时不得形成无限“冷却→重分→静止”且不可观测的循环；服务端兜底未启用时必须明确暴露降级状态和无控制者时长。
11. 不发送客户端退出通知、进程被直接杀死或只有怪物控制子系统失活时，仍能仅靠服务端租约完成回收；退出通知只能缩短恢复时间。

## 八、证据边界

- 视频关键现象依据提供者逐段观察；本报告未把视频帧识别结果当作独立取证来源。
- 标准包速日志主动排除了 `MOVE_LIFE`，因此不能给出事故 Client 最后一条有效怪物移动包的精确时间。
- 现有日志无法区分断网、客户端崩溃、强退或切换异常，不能据此给玩家操作下唯一结论。
- “10:48:11 新登录导致旧残影清理”是时间高度相关的推断；能够确认的是两者几乎同时发生，不能仅靠现有日志证明具体执行了哪条清理分支。

以上限制不影响修复方向：Client 级控制租约与会话代际都以服务端不变量为依据，不依赖猜中玩家当时做了什么操作。
