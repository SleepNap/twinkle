# Twinkle 全局国际化规范

## 1. 语言模型

Twinkle 的 Java 服务端使用一个部署级语言。语言在服务启动时由 `twinkle.service.language` 确定，运行期间不会因账号、游戏会话或 HTTP 请求而改变。当前支持 `zh-CN` 与 `en-US`，默认 `zh-CN`。

```yaml
twinkle:
  service:
    language: ${TWINKLE_SERVICE_LANGUAGE:zh-CN}
```

可用环境变量 `TWINKLE_SERVICE_LANGUAGE` 覆盖配置。配置不支持的语言时服务应启动失败，避免在同一次部署中混用多种后台语言。

## 2. 服务端适用范围

`twinkle.service.language` 控制全部 Java 后台的人类可读文本，包括：

- 运行日志和告警
- 异常及校验提示
- HTTP 响应中的 `message`
- 系统、管理和协议诊断文案
- 包解释器展示的字段说明
- 游戏内玩家提示（交易取消、踢人原因等经 GBK 协议发给玩家客户端的文案）

统一入口是 `core` 模块的 `I18nService`，资源位于 `core/src/main/resources/org/gms/i18n/messages*.properties`，编码为 UTF-8。业务代码使用稳定的 message key；新增文案时必须同时补齐所有支持的语言。

无法经容器注入的代码（游戏对象、静态工具、手动构造的 PacketHandler）经静态门面 `org.gms.i18n.I18n` 取文案（`I18n.message(key, args)`），委托实例由 bootstrap 的 `I18nInitializer`（`@Context`）在进程启动时注入；可注入的 `@Singleton`/`@Controller` 也可直接构造器注入 `I18nService`，二者指向同一实例。

key 前缀约定（单 bundle，前缀区分）：

| 前缀 | 用途 | 占位符 |
|---|---|---|
| `log.*` | 日志模板 | `{}`（slf4j，参数交给 log4j 填充） |
| `error.*` | 异常/校验/HTTP message | `{0}`（MessageFormat） |
| `game.*` | 游戏内玩家提示（发 GBK） | `{0}`（MessageFormat） |

关键约定：日志模板只允许 `{}`（调用时 `I18n.message(key)` **无参**返回原始模板，参数交给 `log.xxx`）；异常/消息/游戏提示只允许 `{0}`（调用时 `I18n.message(key, args...)` **有参**做 MessageFormat 插值）。两者不得混用。

已知例外（架构约束，2 处保留中文硬编码）：`db-dialect` 与 `plugin-api` 是最底层/纯净 SPI 模块，不依赖 `core`（避免循环依赖与 SDK 污染），其技术诊断文案（`DbDialectRegistry` 的「方言注册表不完整」、`ContributionType.fromCode` 的「未知贡献点类型」）保留硬编码。`net-packet` 因需 i18n 已增加对 `core` 的依赖（协议层反向依赖 DI 核心，理想做法是把 I18n 门面下沉到更底层的独立模块，留后续优化）。

下列机器契约不得翻译：

- HTTP `error.code`、JSON 字段名、Tool ID 与 scope
- `RecvOpcode` / `SendOpcode`、十六进制值、包字段稳定 ID
- 配置键、数据库列名、审计事件类型

缺少 message key 时返回 key 本身，以便测试和运维发现资源缺失。审计记录应保存稳定 code/key，显示时再转换为配置语言。

## 3. HTTP 行为

HTTP 请求不能覆盖服务端语言。服务端忽略 `Accept-Language` 对后台文案语言的影响，并在响应的 `Content-Language` 中声明实际配置语言。

客户端必须依赖稳定的 `error.code` 处理错误，不能解析翻译后的 `message`。

## 4. Web 控制台

Web 控制台语言与服务端语言相互独立：

- 文案集中在 `twinkle-web/src/i18n/`，页面通过 `t(messageKey)` 获取文本。
- 用户选择保存在 `localStorage` 的 `twinkle.locale`；首次访问参考浏览器语言，最终回退 `zh-CN`。
- 切换 Web 语言只改变浏览器界面和 `<html lang>`，不会修改服务端、账号或游戏语言。
- 数字、日期和时间使用当前 Web locale 的 `Intl` formatter。

## 5. WZ、脚本与协议编码

WZ 和脚本明确不受 `twinkle.service.language` 控制。

- WZ 只从 `twinkle.wz.path` 指定的目录读取。
- 脚本只从 `twinkle.script.path` 指定的目录读取。
- 服务端不自动拼接语言后缀，不合并目录，不建立 locale overlay，也不回退到其他语言目录。

部署者需要哪套 WZ 或脚本，就直接把对应配置指向那套目录。v83 字符串的线上编码继续使用 GBK；服务端文案语言与协议字符编码是两个独立概念。

**语言与编码的对应规则（部署约定，务必记住）**：

- 语言 `zh-CN` → 部署中文 WZ/script → 中文客户端，协议字符串 GBK 多字节正常显示。
- 语言 `en-US` → 部署英文 WZ/script → 英文客户端，协议字符串为纯英文（ASCII）正常显示。

原因：GBK 是 ASCII 的超集，英文文本用 GBK 编码 = 单字节 ASCII 字节，英文客户端照常读。因此**协议层编码器固定 GBK**（`InPacket.DEFAULT_CHARSET`，读/写字符串均走它），`twinkle.service.language` 只改文案**内容**（中文↔英文），不改编码；HTTP 固定 UTF-8。ASCII 不是独立的编码选项，只是"英文文本在 GBK 下的表现"。开源后国外玩家换英文 WZ/script + `en-US` 配置即可玩。

## 6. 开发与验收

- 新增 Java 后台可见文案时，使用稳定 key，并同步补齐 `zh-CN`、`en-US` 资源。
- 服务端测试覆盖两种配置语言、缺失 key、参数插值和不支持语言的启动失败。
- API 集成测试校验 `Content-Language` 等于服务端配置语言，并验证 `Accept-Language` 不能覆盖它。
- Web 检查语言目录 key 集合一致，并覆盖导航、对话框、Toast、空状态和错误状态的语言切换。
- WZ 与脚本加载测试只验证显式路径，不得引入对 `twinkle.service.language` 的依赖。
