# AI / Agent 架构形态决策记录（2026-08-10）

**决策性质**：AI 与 Agent 在 twinkle 中的定位、边界与仓库归属
**触发背景**：数据库全面重写后前端形态尚未设计（twinkle-web 被整体删除），趁此时机厘清"AI/Agent/Web/服务端能力"四者的关系，避免按错误方向投入
**讨论方**：项目所有者 × Claude

---

## 一、决策背景

项目已完成 M0-M6，服务端能力齐备（HTTP / AI / 插件 / 热更新 / 分布式）。前端形态空白待设计。围绕"AI 到底怎么融入"存在四个矛盾，逐一厘清后收敛为本文档的结论。

### 矛盾 1：API-key 指什么？

> **指对外接口的访问凭据，不是大模型 key。**

- 服务端要对外暴露能力，除了 JWT 之外，需支持 **API-key 验证方式**。
- 参考 Codex 的模式：**登录授权后签发 API-key**，第三方/工具凭 key 调接口。
- 大模型自己的 key（OpenAI 等）是另一回事，走环境变量注入，不在此列。

### 矛盾 2：AI 到底放服务端还是前端？

> 后端只提供**接口和能力**，agent 的"编排/上下文/智慧"放**外部 agent 客户端**。

- 后端没必要承载 agent 的思维。
- 数据在服务端（频道 Netty 进程、内存态权威），能力只能由服务端暴露；但**暴露成纯接口**即可，agent 逻辑交给外部。

### 矛盾 3：为什么又想要前端/客户端 agent？

> 因为客户端 agent 能组合两路能力：服务端能力 + 本地能力。

- **服务端能力**：游戏内操作、DB、日志、排查（经接口暴露）。
- **本地能力**：把返回数据转 Excel / 图片 / Markdown，联网搜索，本地知识库，记忆。
- 这些本地能力**不该也不适合在后端做**（2C2G、无浏览器、无本地文件），天然属于客户端 agent。

### 矛盾 4：服务端到底要不要做 agent 宿主？

> **保留，但做成可选功能（同 WAL 按需启用）。**

- 服务端 agent 宿主的价值在"能调游戏工具"，而工具建立在服务端能力面上——拆出去等于把最有价值的一半留在 twinkle，是自残。
- 服务端 agent 在"人/外部 agent 驱动"场景下确实比外部 agent 笨（没有本地工具、联网、记忆），但存在**外部 agent 覆盖不了**的场景：
  - **玩家触发游戏事件 → AI 自动响应**（GM 自动陪玩、事件自动处理）——触发者在游戏内，外部 agent 不在；
  - **日志突变 → AI 自动分析告警**——监控在服务端，没人盯着外部 agent。
- 这两个场景是"服务端主动"的：触发者是游戏事件 / 系统状态，不是"人/外部 agent"。此时服务端 agent **不可替代**。
- 但 2C2G 红线扛不住服务端 AI 常驻扩展 → **必须像 WAL 一样做成可选功能**：默认不装配，`twinkle.ai.enabled=true` 显式启用。

## 二、决策结论

### 决策 1：服务端 = 能力面（主）+ 可选 agent 宿主（辅）

服务端定位为**能力提供方**，只做四件事：

| 能力面组件 | 说明 |
|---|---|
| **REST 接口** | 读/写游戏数据、DB、日志、排查，整理成清晰的接口清单 |
| **API-key 鉴权** | JWT + API-key 双通道；登录授权后签发 key，可轮换/吊销 |
| **scope 授权** | 能力分级：读类（在线状态/日志/DB 查询）vs 写类（操作游戏/改 DB），按 scope 授权 |
| **审计** | 调用日志落库（谁用哪个 key 调了什么） |

**外部 agent 调能力面**（api-key + scope + 审计），服务端只执行、不思考。

**同时保留服务端 agent 宿主（可选）**：覆盖"玩家触发游戏事件 / 日志突变"这类服务端主动场景。默认不装配，`twinkle.ai.enabled=true` 显式启用（2C2G 红线，同 WAL）。

### 决策 2：agent 宿主保留（可选），不拆出项目

| 东西 | 去留 | 理由 |
|---|---|---|
| `AiServices` + `LocalRuleChatModel` + 工具编排（现 `ai/` 模块） | **保留，可选装配**（`twinkle.ai.enabled=true` 启用） | 覆盖"服务端主动"场景（游戏事件/日志告警）；外部 agent 无法覆盖这类触发 |
| **LLM 客户端**（一个 `ChatModel` bean，调外部 LLM 生成叙述） | **保留**（随 agent 可选装配） | 定时任务喂数据 → LLM 生成叙述 → 展示；走 `TWINKLE_LLM_API_KEY` env |
| **能力面**（REST + api-key + scope + 审计） | **主投** | 外部 agent、web、定时任务的共同底座 |

**为什么不拆出项目**：agent 宿主的全部价值在"能调游戏工具"，工具建立在服务端能力面上（`AdminService`/core 契约）——拆出去 = 只搬走通用壳、留下最有价值的一半，是自残。留在 twinkle 里当模块（现状 `ai/`），按能力面解耦设计，将来真要拆 = 搬目录 + 带契约，纯机械动作。

### 决策 3：agent 客户端独立仓库，不放本项目

> **命名：twish**（2026-08-10 定）。合成词 twinkle（闪闪）× wish（愿），与 twinkle 成"tw"前缀一对。设计来源：twinkle 的"闪闪"承载"星愿"，agent 是帮玩家实现心愿的助手（客服能力即此角色的具象）。项目名用英文（中文无法命名项目），twish 为自造词，需接受对外解释成本。

```
twinkle 仓库（服务端） ──▶ 能力面 HTTP + api-key ──▶ twish（独立仓库）
   Java / Maven / 2C2G                                 CLI / 本地工具 / 记忆
```

- 耦合只剩一张契约（OpenAPI 描述），分开成本几乎为零。
- agent 客户端注定要装模型配置、工具注册、本地知识库、记忆——这些与"服务端"无关，放进来即臃肿。
- 例外：若它只是几十行调用脚本，先放 `twinkle-server/scripts/`，等长大再拆。
- 判断标准：**它会长大吗？会，就现在独立；不会，就留 scripts/。**

### 决策 4：twinkle-web 留在本仓库

| | twinkle-web | twish（agent 客户端） |
|---|---|---|
| 与服务端关系 | **不可分割的展示层**（同一个"控制台"功能） | 独立工具（能连任何能力面） |
| 迭代节奏 | 跟服务端功能走 | 快（模型/工具/本地能力高频变） |
| 复用性 | 只服务 twinkle | 可服务多个后端 |

web 是服务端的一部分，twish 是消费者，两者归属不同。

### 决策 5：敏感操作必须服务端授权 + 审计

> **执行的权力在服务端，编排的智慧在客户端 agent。**

- 访问游戏内存、操作 DB、操作日志这类"危险但排查有用"的能力，**不能由客户端 agent 直接执行**（客户端不可信、无法审计）。
- 改为：客户端 agent 调 `/api/v1/admin/*` → 服务端鉴权 + 执行 + 审计 → 结果 JSON 回客户端 agent 加工展示。
- 相比旧做法（客户端 SSH 到服务器、所有指令由 agent 执行）是**安全提升**，方向正确。
- 这与现有 `AdminService`（core 契约）模式一致——`GameStatTool` 已是"服务端执行、结果回前端"的样板，要推广成通用能力面。

---

## 三、最终形态（一句话）

> **服务端 = 能力面（REST + api-key + scope + 审计）+ 可选 agent 宿主（`twinkle.ai.enabled`，2C2G 默认关）+ 薄 LLM 客户端。外部 agent = 智慧。web = 能力面的可视化。**

三个独立的东西：**twinkle（服务端）、twinkle-web（控制台）、twish（agent 客户端）**。服务端与 twish 之间只靠 api-key + OpenAPI 说话，谁都不臃肿谁。服务端 agent 宿主作为可选能力保留在 twinkle 内，不拆不删，覆盖"服务端主动"场景。

## 四、权衡与备选

### 服务端 agent 宿主：留 vs 不留

**核心论据：客服能力（AI 值班 GM）。**

> 玩家在游戏里打字："GM 在吗，我昨天花 5000 万买的装备今天不见了"。
>
> 服务端 agent 需要：① 理解这句开放式的自然语言 → 判定是"装备丢失"类问题；② 自主决定查什么 → 背包 / 交易 / 时间点操作 / 是否回档；③ 据查证结果判定（正常流失？被脚本骗走？吞了？）；④ 用自然语言回应玩家（基于实际查到的数据组织回答）。

为什么这个场景**必须**服务端 agent：

- **代码/规则做不到**：玩家的问题是开放式自然语言（"不见了"、"被吞了"、"给人骗了"、"回档了"…不可枚举），代码没法给每种说法写规则；回答也不能是模板，要基于实际查证组织语言。
- **外部 agent 做不到**：玩家在游戏内跟 AI 说话，触发在服务端频道进程；取证要查频道内存投影 / DB / 交易链，需服务端内部视图 + 写审计。外部 agent 不在服务端，也没有这个实时内部视角。
- **定时任务 + 单次 LLM 做不到**：②③ 是决策链——查完背包才发现要查交易，查完交易才发现要查时间点。每步查什么是上一步结果决定的，无法预先写成固定脚本。

**一句话**：AI 在服务端的核心价值 = "理解玩家/管理员说了什么，自主决定查什么，再用自然语言回应"。代码理解不了开放语言，外部 agent 进不了服务端内部——**两者都跨不过，只有服务端 agent 能。**

其余场景（判断它们**不需要** agent 宿主，避免为不存在的需求保留）：

| 场景 | 需要 agent 宿主吗 | 原因 |
|---|---|---|
| 用户问"现在在线多少人"（外部 agent 驱动） | ❌ | 外部 agent 调能力面即可 |
| 用户排查 bug（外部 agent 驱动） | ❌ | 同上 |
| 每日运营日报 | ❌ | 定时收集 + 单次 LLM 生成叙述就够 |
| 阈值告警（如在线暴跌 30%） | ❌ | 规则引擎即可，不需语义 |
| 定时调节刷怪节奏 | ❌ | 状态机即可 |

**结论**：因存在"客服能力"这一不可替代场景，**保留服务端 agent 宿主，但 2C2G 默认关、按需启用**（同 WAL，`twinkle.ai.enabled`）。

### agent 宿主"拆出去"：暂不拆，设计成随时能拆

- 宿主的通用壳（LangChain4j + 记忆 + RAG + 模型路由）随处可得，价值在**能调什么工具**——而工具建立在能力面上，必须留 twinkle。
- 拆的条件（三条，当前均未出现）：**第二个消费者出现 / 宿主膨胀 / 独立发布节奏**。
- 做法：agent 宿主只依赖"能力接口 + 工具 SPI"，不依赖游戏具体类。将来要拆 = 搬模块目录 + 带 HTTP 契约，纯机械动作。

## 五、后续行动（按优先级）

1. **能力面设计（twish v0.1 只读闭环已完成 2026-08-11）**：稳定服务端身份、Subject/Credential、专用 scope、身份快照、Capability 摘要与详情、统一 Tool 执行、健康与在线分页 Tool、标准信封和 `auditRef` 已落地；接入说明见 [`twish-capability-api.md`](twish-capability-api.md)。
2. **ai 模块可选化（已完成 2026-08-10）**：`AiEnabledCondition` + `twinkle.ai.enabled`（默认 false），管理进程 + 开关双条件才装配；默认 2C2G 不装配省资源。
3. **服务端 agent 完善（启用后，核心方向=客服能力）**：接入真实 LLM（`ChatModel` bean 换 OpenAI/Ollama，api-key 走 env）→ 落地"AI 值班 GM"：理解玩家自然语言 → 服务端取证（背包/交易/DB，写审计）→ 自然语言回应。这是 agent 保留的立足点。
4. **web 控制台**：作为能力面的可视化，后做。
5. **twish（agent 客户端）**：独立仓库，先最小化（登录授权签 key → 调能力面），再逐步加本地工具。
6. **第三方 IM 渠道（服务端侧）**：微信 / 飞书 / Telegram / Discord 的 webhook 接入层在服务端，收消息 → 结构化解析 → 入能力面事件收件箱 → twish 补拉/订阅发起任务；twish 亦经能力面向 IM 推送结果/告警/审批（两端都做）。IM 文本按不可信输入处理，防提示词注入。

## 六、关键约束回顾（与现有红线一致）

- AI 工具/接口不得直踩游戏内存对象，只经 `AdminService`（core 契约）——红线 3。
- HTTP 与游戏 Netty 隔离 EventLoop——红线 6。
- 2C2G 强制单进程；能力面与薄 LLM 客户端都是低频、无状态，可并进管理进程——红线 15。
- API-key 不入源码，走环境变量/配置注入——安全红线 22。
