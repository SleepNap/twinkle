# AI / Agent 架构形态决策记录（2026-08-10）

**决策性质**：AI 与 Agent 在 twinkle 中的定位、边界与仓库归属
**触发背景**：数据库全面重写后前端形态尚未设计（twinkle-web 被整体删除），趁此时机厘清"AI/Agent/Web/服务端能力"四者的关系，避免按错误方向投入
**讨论方**：项目所有者 × Claude

---

## 一、决策背景

项目已完成 M0-M6，服务端能力齐备（HTTP / AI / 插件 / 热更新 / 分布式）。前端形态空白待设计。围绕"AI 到底怎么融入"存在四个矛盾，逐一厘清后收敛为本文档的结论。

### 矛盾 1：API-key 指什么？

> **指对外接口的访问凭据，不是大模型 key。**

- 服务端要对外暴露能力，除了 JWT 之外，需支持 **API-key 验证方式**。
- 参考 Codex 的模式：**登录授权后签发 API-key**，第三方/工具凭 key 调接口。
- 大模型自己的 key（OpenAI 等）是另一回事，走环境变量注入，不在此列。

### 矛盾 2：AI 到底放服务端还是前端？

> 后端只提供**接口和能力**，agent 的"编排/上下文/智慧"放**外部 agent 客户端**。

- 后端没必要承载 agent 的思维。
- 数据在服务端（频道 Netty 进程、内存态权威），能力只能由服务端暴露；但**暴露成纯接口**即可，agent 逻辑交给外部。

### 矛盾 3：为什么又想要前端/客户端 agent？

> 因为客户端 agent 能组合两路能力：服务端能力 + 本地能力。

- **服务端能力**：游戏内操作、DB、日志、排查（经接口暴露）。
- **本地能力**：把返回数据转 Excel / 图片 / Markdown，联网搜索，本地知识库，记忆。
- 这些本地能力**不该也不适合在后端做**（2C2G、无浏览器、无本地文件），天然属于客户端 agent。

### 矛盾 4：服务端到底要不要做 agent 宿主？

> **不做。** 但留一个极薄的 LLM 客户端，为未来留干净入口。

- 若只是"定时任务收集数据 + 事后整理成日报"，**纯代码即可**，连 agent 都不用；顶多需要一个 LLM 调用生成自然语言叙述，不需要"多步推理 + 工具编排"的 agent 宿主。
- 服务端 agent 宿主的全部价值在"能调游戏工具"，而工具建立在服务端能力面上——拆出去等于把最有价值的一半留在 twinkle，是自残。
- 且服务端 agent 注定比外部 agent 笨（没有本地工具、联网、记忆），没有存在价值。

---

## 二、决策结论

### 决策 1：服务端 = 能力面，不做 agent 宿主

服务端定位为**能力提供方**，只做四件事：

| 能力面组件 | 说明 |
|---|---|
| **REST 接口** | 读/写游戏数据、DB、日志、排查，整理成清晰的接口清单 |
| **API-key 鉴权** | JWT + API-key 双通道；登录授权后签发 key，可轮换/吊销 |
| **scope 授权** | 能力分级：读类（在线状态/日志/DB 查询）vs 写类（操作游戏/改 DB），按 scope 授权 |
| **审计** | 调用日志落库（谁用哪个 key 调了什么） |

**外部 agent 调能力面**（api-key + scope + 审计），服务端只执行、不思考。

### 决策 2：agent 宿主不留，LLM 客户端留

| 东西 | 去留 | 理由 |
|---|---|---|
| `AiServices` + `LocalRuleChatModel` + 工具编排（现 `ai/` 模块的 agent 部分） | **不投入，不在路线图** | 多步推理重活，当前场景用不上；注定比外部 agent 笨 |
| **LLM 客户端**（一个 `ChatModel` bean，调外部 LLM 生成叙述） | **留** | 极薄（一个 bean + 一个接口方法），定时任务喂数据 → LLM 生成叙述 → 展示。走 `TWINKLE_LLM_API_KEY` env |
| **能力面**（REST + api-key + scope + 审计） | **主投** | 外部 agent、web、定时任务的共同底座 |

### 决策 3：agent 客户端独立仓库，不放本项目

```
twinkle 仓库（服务端） ──▶ 能力面 HTTP + api-key ──▶ agent 客户端（独立仓库）
   Java / Maven / 2C2G                                 CLI / 本地工具 / 记忆
```

- 耦合只剩一张契约（OpenAPI 描述），分开成本几乎为零。
- agent 客户端注定要装模型配置、工具注册、本地知识库、记忆——这些与"服务端"无关，放进来即臃肿。
- 例外：若它只是几十行调用脚本，先放 `twinkle-server/scripts/`，等长大再拆。
- 判断标准：**它会长大吗？会，就现在独立；不会，就留 scripts/。**

### 决策 4：twinkle-web 留在本仓库

| | twinkle-web | agent 客户端 |
|---|---|---|
| 与服务端关系 | **不可分割的展示层**（同一个"控制台"功能） | 独立工具（能连任何能力面） |
| 迭代节奏 | 跟服务端功能走 | 快（模型/工具/本地能力高频变） |
| 复用性 | 只服务 twinkle | 可服务多个后端 |

web 是服务端的一部分，agent 客户端是消费者，两者归属不同。

### 决策 5：敏感操作必须服务端授权 + 审计

> **执行的权力在服务端，编排的智慧在客户端 agent。**

- 访问游戏内存、操作 DB、操作日志这类"危险但排查有用"的能力，**不能由客户端 agent 直接执行**（客户端不可信、无法审计）。
- 改为：客户端 agent 调 `/api/v1/admin/*` → 服务端鉴权 + 执行 + 审计 → 结果 JSON 回客户端 agent 加工展示。
- 相比旧做法（客户端 SSH 到服务器、所有指令由 agent 执行）是**安全提升**，方向正确。
- 这与现有 `AdminService`（core 契约）模式一致——`GameStatTool` 已是"服务端执行、结果回前端"的样板，要推广成通用能力面。

---

## 三、最终形态（一句话）

> **服务端 = 能力面（REST + api-key + scope + 审计）+ 定时任务 + 薄 LLM 客户端。外部 agent = 智慧。web = 能力面的可视化。服务端不做 agent 宿主。**

三个独立的东西：**twinkle（服务端）、twinkle-web（控制台）、agent 客户端**。服务端与 agent 之间只靠 api-key + OpenAPI 说话，谁都不臃肿谁。

---

## 四、权衡与备选

### 服务端 agent 宿主：留 vs 不留

| 场景 | 需要服务端 agent 宿主吗 |
|---|---|
| 用户问"现在在线多少人"（外部 agent 驱动） | ❌ 不需要 |
| 用户排查 bug（调 DB/看日志，外部 agent 驱动） | ❌ 不需要 |
| 每日凌晨生成运营日报落库 | ✅ 但只需**定时任务 + LLM 客户端**，不需要 agent 宿主 |
| 玩家触发游戏事件 → AI 自动响应 | ✅ 需要（当前无此场景） |
| 日志突变 → AI 自动分析告警 | ✅ 需要（当前无此场景） |

**判断标准**：AI 使用是否永远由"人/外部 agent"发起？是 → 服务端只是能力面；有定时/事件驱动 → 才考虑轻量宿主。

### agent 宿主"拆出去"：暂不拆，设计成随时能拆

- 宿主的通用壳（LangChain4j + 记忆 + RAG + 模型路由）随处可得，价值在**能调什么工具**——而工具建立在能力面上，必须留 twinkle。
- 拆的条件（三条，当前均未出现）：**第二个消费者出现 / 宿主膨胀 / 独立发布节奏**。
- 做法：agent 宿主只依赖"能力接口 + 工具 SPI"，不依赖游戏具体类。将来要拆 = 搬模块目录 + 带 HTTP 契约，纯机械动作。

## 五、后续行动（按优先级）

1. **能力面设计**（第一优先级）：接口清单 + scope 分级 + api-key 鉴权 + 审计。这是外部 agent、web、定时任务的共同底座。
2. **薄 LLM 客户端**：一个 `ChatModel` bean（OpenAI 兼容，api-key 走 env），对接"定时数据 → LLM 生成叙述 → 日报"最小闭环。
3. **停止投入** `ai/` 模块的 agent 编排部分（`AiServices` + `LocalRuleChatModel`），明确不在路线图；不急着删，作为能力保留。
4. **web 控制台**：作为能力面的可视化，后做。
5. **agent 客户端**：独立仓库，先最小化（登录授权签 key → 调能力面），再逐步加本地工具。

---

## 六、关键约束回顾（与现有红线一致）

- AI 工具/接口不得直踩游戏内存对象，只经 `AdminService`（core 契约）——红线 3。
- HTTP 与游戏 Netty 隔离 EventLoop——红线 6。
- 2C2G 强制单进程；能力面与薄 LLM 客户端都是低频、无状态，可并进管理进程——红线 15。
- API-key 不入源码，走环境变量/配置注入——安全红线 22。
