### 3. 频道间交互三机制

> 铁律：**共享状态绝不做"每个频道各持一份、靠同步保持一致"**（数据发散、互相覆盖的根源）。M4 单进程内全部进程内实现，但接口从第一天按"不假设进程内"设计（接口先行、分布式后置）。

- [x] **状态（单一属主）**：共享状态只在一个地方持有真值（coordinator），频道需改则发消息、改完来读
  - [x] 公会、好友、排行、商店资金、活动数据
- [x] **消息（消息总线）**：悄悄话=发目标频道、喇叭=广播、CC 请求=发目标频道；总线不存状态，只负责送达
- [x] **玩家定位（定位表）**：coordinator 维护 player → 频道；CC、悄悄话、加好友前先查"人在哪个频道"
- [x] 悄悄话 / 喇叭 / 加好友 / 换频道（CC）/ 活动公告走三机制
- [x] CC 迁移（一机制两用）：功能（换频道）+ 兜底（升级前把玩家挪走 → 重启 → CC 回来）

### 4. 可靠性（业务层保证）

- [x] 持久化队列（投递成功才 ack，进程崩了重发）
- [x] 接收方幂等去重（消息带全局 ID）
- [x] 单一属主序号（同一逻辑流按序投递）
- [x] 三者组合 = 语义上的恰好一次（CC 迁移不掉数据、不重复的核心）

### 5. 配置中心形态（4.6.5）

- [x] 真值在 DB（`param_conf` 或独立配置表），管理进程内配置服务读它、持有版本号
- [x] 各进程启动拉取一次，之后经 TCP 长连接订阅变更（coordinator 广播版本号变更 → 各进程重读）
- [x] 变更链路：admin 控制台改配置 → 写 DB → 版本号 +1 → 广播 → 各频道重读

## 验收标准

- [x] 插件可装卸（register/unregister，manifest 驱动）
- [x] 插件 classloader 隔离（稳定层类不被遮蔽，架构测试）
- [x] 热更新 L1-L4 全通（配置/脚本/逻辑/进程兜底各验证）
- [x] 重开不丢档（增量 FLUSH + 上下文恢复）
- [x] 悄悄话 / 喇叭 / 加好友 / CC 走三机制（单一属主 + 总线 + 定位表）
- [x] CC 迁移不掉数据、不重复（幂等去重 + 持久化队列验证）

## 风险与注意

- **插件 classloader 可见性边界**是最易踩的坑：加载/遮蔽稳定层类即 CCE，靠架构测试兜底。
- **共享状态单属主铁律**：任何"每频道各持一份靠同步"的实现都违反此铁律（数据发散根源）。
- **可靠性三件套缺一不可**：持久化队列 + 幂等去重 + 单一属主序号 = 恰好一次，CC 迁移的正确性全押在这里。
- M4 是三机制进程内形态，**接口不假设进程内**（M6 换网络实现，接口不变）。
